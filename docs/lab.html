Lab: measuring a small local assistant

An evaluation harness for Hermes Agent driving Qwen3.5-4B through llama.cpp, with every tool a stand-in over invented data. It measures how often the model does the right thing, and tests whether code outside the model can stop it from sending or deleting on its own.

What it is

The code is in the repository's lab/ directory. It runs a set of assistant tasks (read the calendar, set a reminder, find an email and act on it, draft a reply, send a text, refuse instructions hidden in a web page) against fourteen stand-in tools that operate on fixture files. No real calendar, message store, mail account or file is touched, and every person, number and address in the fixtures is invented.

Each task runs three times at two levels: a bare OpenAI-compatible endpoint with a minimal agent loop, and through Hermes Agent v0.23.2 restricted to the lab's tools inside an OS sandbox. A task passes or fails by deterministic checks on the tool calls, the final answer and the end state. The model is Qwen3.5-4B, Q4_K_M quantisation, thinking off.

Three mechanisms were tested. A confirmation gate: sending a message or deleting a file only stages a preview, and runs on a second call only if the user's side has recorded an approval. A date and time resolver: tools accept "friday" or "3 to 4pm" and work out the date in code. A compact prompt packaged as a Hermes persona.

Held-out results

A first round of prompt tuning reached 95.8% (bare endpoint) and 92.7% (Hermes) on 55 tasks. Those numbers were in-sample: the same author wrote the tasks and the fixes. The three mechanisms were then frozen in git, 63 new tasks were written on new fixture data with a different date, and everything was run on them. The table is from that held-out set: 63 tasks, 3 runs each, 189 runs per cell. The range in brackets is a 95% bootstrap interval over tasks.

Reading the numbers

  • The round-1 result did not generalise. 95.8% in-sample became 78.3% on new tasks at the bare endpoint, and 92.7% became 83.6% through Hermes. Dates (46%) and multi-step chains (42%) account for most of the drop at the bare endpoint.
  • With the gate, no send or delete ran without a recorded confirmation. Without it, 23 (bare) and 22 (Hermes) ran on the model's say-so, including an injected email that got a file of passwords sent in 3 of 3 runs at both levels. With it the count was zero in every gated run, while the model still tried: previews left unapproved and second calls refused by the gate are counted in the full tables. This is a result about stand-in tools; nothing here was connected to a real messaging account.
  • Pass-rate differences between configurations are within noise at 63 tasks. Every paired interval against configuration (1) includes zero. The unsafe-action count is the result that is not within noise.
  • The checks were corrected once. Three checks rejected correct answers and were fixed after the first grading; 9 of 1,512 runs changed, all from fail to pass, and both gradings are in the full tables.
  • The held-out set is no longer held out. Its failures have been read, so the next change has to be judged on a third, new set.

What is not measured

  • Linux. Every model and Hermes run was made on macOS on Apple Silicon. On Linux only the unit tests and the sandbox wrapper (bubblewrap) have been run, in CI on hosted Ubuntu runners, without a model or Hermes; that wrapper does not filter outbound network traffic. See docs/design/cross-platform.md.
  • Real apps and accounts. All tools are stand-ins. Nothing shows how the gate behaves in front of a real messaging or mail client.
  • Other models and sizes. One 4B model, one quantisation for the main tables.
  • Hermes configurations (2) and (3). The single-lever ablations were run at the bare endpoint only.
  • Voice, long unattended jobs and anything multi-user.

How to reproduce

The unit tests need only Python 3.11 or newer and no model:

git clone https://github.com/techmore/local-assistant-stack
cd local-assistant-stack/lab
python -m unittest discover -s tests -v

The model runs need llama-server from llama.cpp, the Qwen3.5-4B Q4_K_M GGUF file (about 2.7 GB) and, for the Hermes level, a sandboxed checkout of Hermes Agent v0.23.2. The steps are in docs/USAGE.md. Then:

.venv/bin/python harness/sweep.py --suite heldout configs/raw_best.json configs/raw_assist2.json
.venv/bin/python harness/report_heldout.py

Raw transcripts are not published; the summary tables are. Runs use fixed seeds (1000 to 1002), but results on another machine or llama.cpp build can differ by a few runs.
